# 看板调度规范 📋

> 定义 Kanban 任务的调度逻辑：默认走闪莉，特殊任务才指定。

---

## 一、核心原则

> **核心原则**：所有看板任务默认由闪莉执行，闪莉的模型调用逻辑详见《莉莉丝的工作规范》第三章「闪莉竞速机制」。**创建看板任务时，必须按本规范指定执行者，不得省略参数随意创建。**

```
看板创建任务
  ↓
默认 → ⚡ 闪莉（按工作规范选最快的 mimi/light/deep 模型）
  ↓
特殊任务 → 手动指定（小莉/莉莉/大莉）
```

---

## 二、闪莉模型调用逻辑（引用工作规范）

闪莉的竞速机制和模型选择由工作规范定义，这里只做概要引用：

| 分类 | 模型来源 | 适用场景 |
|:----:|:---------|:---------|
| ⚡ **mimi** | Ping mimi 分类（小模型） | 轻量任务、高峰期替补 |
| 🚀 **light** | Ping light 分类（主力模型） | 日常任务 |
| 🧠 **deep** | Ping deep 分类（强模型） | 深度分析 |
| 🖼️ **vision** | Ping vision 分类（多模态） | 看图/网页/视频 |

详见 `~/.hermes/莉莉丝的工作规范.md` → **三、闪莉竞速机制**

## 三、Profile 定义（看板技术配置）

| Profile | 模型 | Provider | 说明 |
|:-------:|:----:|:--------:|:------|
| **default** | deepseek-v4-flash | DeepSeek 官方 API | 看板任务默认执行通道。worker 启动后，根据任务复杂度决定是否 delegate 给闪莉（详见下方"四、执行链路"） |
| **xiaoli** | gemma-4-e4b | 本地 localhost:1234 | 纯本地操作。需手动指定 `--assignee xiaoli` |

> Profile 决定看板 worker 用哪个基座模型启动。worker 内部的子代理调度（闪莉/闪莉mimi/莉莉/大莉）由工作规范定义，通过 `delegate_task` 实现，与 Profile 是两个独立层面。

---

## 四、执行链路

看板任务的实际执行流程：

```
kanban create "长篇扫榜"
  ↓
dispatcher → 启动 default worker（deepseek-v4-flash）
  ↓
worker 收到任务，判断复杂度
  ├── 复杂任务 → delegate_task 派 闪莉（NVIDIA/OpenRouter/Google 竞速）
  ├── 轻量任务 → delegate_task 派 闪莉mimi（mimi 分类小模型）
  ├── 审核任务 → delegate_task 派 莉莉（ChatAnywhere→DeepSeek）
  ├── 核弹任务 → delegate_task 派 大莉（deepseek-v4-pro）
  └── 纯本地  → 直接让 xiaoli 执行
```

> **"默认走闪莉"的含义**：看板 worker 启动后，对于需要联网或较强能力的任务，会 delegate 给闪莉执行，而非 worker 自己硬做。闪莉的模型选择由 Ping 排名自动决定。

---

## 四、特殊任务指定

非默认情况才需要手动指定：

```bash
# 需要小莉（本地）
hermes kanban create "任务名" --assignee xiaoli

# 需要莉莉（ChatAnywhere 免费通道）
# 目前看板不支持直接指定莉莉通道，需走 default 后手动 delegate_task

# 需要大莉（核弹）
# 闪莉全失败后自动兜底，无需手动指定
```

## 五、超时与重试

| 参数 | 默认值 | 说明 |
|:-----|:------:|:------|
| max-runtime | 8m（config.yaml 全局默认） | 普通任务最长执行时间 |
| max-retries | 2 | 失败重试次数 |
| failure_limit | 2 | 连续失败后变 blocked |
