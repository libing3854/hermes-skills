# 看板调度规范 📋

> 定义 Kanban 任务的调度逻辑：谁执行、用什么模型、超时重试策略。

---

## 一、Profile 定义

| Profile | 模型 | 用途 | 费用 |
|:-------:|:----:|:----:|:----:|
| **default** | deepseek-v4-flash | 主力执行（≈闪莉） | 🟡 免费 |
| **xiaoli** | gemma-4-e4b（本地 4B） | 轻量任务（≈小莉） | 🟢 免费 |

---

## 二、任务类型 → Profile 映射

| 任务类型 | 分给 | 模型 | 说明 |
|:---------|:----:|:----:|:------|
| 📖 **长篇扫榜/拆文/写作** | default | deepseek-v4-flash | 需要联网搜索+分析能力 |
| 📖 **短篇扫榜/拆文/写作** | xiaoli | gemma-4-e4b | 轻量任务，本地处理 |
| 📰 **资讯采集/整理** | default | deepseek-v4-flash | 需要联网搜索 |
| 💹 **金融数据处理** | default | deepseek-v4-flash | 需要运行脚本 |
| 🧹 **去AI味/审稿** | xiaoli | gemma-4-e4b | 纯文本处理，本地够用 |
| 🔍 **纯搜索任务** | default | deepseek-v4-flash | 需要联网 |
| 💻 **代码/脚本执行** | default | deepseek-v4-flash | 需要运行能力 |
| 🏠 **本地文件操作** | xiaoli | gemma-4-e4b | 纯本地，不需要联网 |

### 分配优先级

1. 按任务类型匹配上表
2. 如果任务声明了 `--assignee`，以声明的为准
3. 如果任务带有 `--skill`，按 skill 的 decompose 逻辑分配
4. 以上都不匹配 → 默认分给 default profile

## 三、超时与重试策略

| 参数 | 默认值 | 说明 |
|:-----|:------:|:------|
| max-runtime | 10m | 普通任务最长执行时间 |
| max-runtime（扫榜） | 15m | 需要搜索多个网站 |
| max-runtime（金融看板） | 5m | 脚本执行较快 |
| max-retries | 2 | 失败后最多重试 2 次 |
| failure_limit | 2 | 连续失败 2 次后变 blocked |

### 超时处理流程

```
任务超时 → SIGTERM → 5s后 SIGKILL → 重试
  ├── 重试成功 → 继续
  └── 重试 failure_limit 次仍失败 → blocked（人工处理）
```

## 四、创建任务时的推荐参数

```bash
# 长篇扫榜（给闪莉）
hermes kanban create "长篇扫榜" \
  --body "..." \
  --max-runtime 15m \
  --skill story-long-scan

# 短篇扫榜（给小莉）
hermes kanban create "短篇扫榜" \
  --body "..." \
  --max-runtime 15m \
  --assignee xiaoli \
  --skill story-short-scan

# 简单文本处理（给小莉）
hermes kanban create "去AI味" \
  --body "..." \
  --max-runtime 5m \
  --assignee xiaoli
```

## 五、看板与工作规范的关系

| | 工作规范（莉莉丝的工作规范.md） | 看板调度规范（本文件） |
|:--|:-------------------------------|:---------------------|
| **范围** | 我主动派活时的决策逻辑 | 看板自动调度时的分配逻辑 |
| **场景** | delegate_task、组合代理模式 | kanban dispatcher 自动分配 |
| **执行者** | 我（莉莉丝）手动选择 | gateway dispatcher 自动调度 |

> **核心原则**：看板调度规范的分配逻辑应与工作规范一致——长篇/复杂任务给闪莉（default），短篇/轻量任务给小莉（xiaoli）。
