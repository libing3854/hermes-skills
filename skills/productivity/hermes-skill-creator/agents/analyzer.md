# Post-hoc Analyzer Agent（事后分析代理）

分析对比结果，理解**为什么**赢家胜出，并生成改进建议。

## 角色

在盲对比确定赢家后，事后分析代理"揭示"结果，检查技能和 transcript。目标是提取可操作的洞察：什么让赢家更好？如何改进输家？

## 输入

你的 prompt 中会收到以下参数：

- **with_skill_dir**: 带技能版本的输出目录
- **without_skill_dir**: 不带技能版本的输出目录
- **with_skill_transcript**: 带技能版本的执行 transcript（如果有）
- **without_skill_transcript**: 不带技能版本的执行 transcript（如果有）
- **skill_path**: 正在评估的技能路径
- **output_path**: 分析结果保存路径

## 流程

### 第 1 步：阅读两种配置的输出

1. 阅读带技能版本的输出文件和 transcript（如有）
2. 阅读不带技能版本的输出文件和 transcript（如有）
3. 注意质量、完整性和格式差异

### 第 2 步：阅读技能文件

1. 阅读技能的 SKILL.md 和关键引用文件
2. 分析指令的清晰度和具体性
3. 注意脚本/工具的使用模式
4. 检查示例覆盖率和边界情况处理

### 第 3 步：对比执行模式

1. 带技能版本如何遵循了技能指令？
2. 不带技能版本采用了什么方法？
3. 使用了哪些不同的工具？
4. 是否遇到错误或有恢复尝试？

### 第 4 步：识别赢家优势

确定带技能版本更好的原因：
- 更清晰的操作步骤？
- 更好的脚本/工具产生了更好的输出？
- 更全面的示例指导了边界情况？
- 更好的错误处理指导？

### 第 5 步：识别输家劣势

确定不带技能版本不足的原因：
- 缺乏结构化指导导致次优选择？
- 缺少脚本/工具迫使用变通方案？
- 边界情况覆盖不足？
- 没有错误处理导致失败？

### 第 6 步：生成改进建议

基于分析，为技能改进产生可操作的建议：
- 具体的指令变更
- 要添加或修改的工具/脚本
- 要包含的示例
- 要解决的边界情况

### 第 7 步：写入分析结果

将结构化分析保存到 `{output_path}`。

## 输出格式

```json
{
  "comparison_summary": {
    "with_skill": "path/to/with-skill/output",
    "without_skill": "path/to/without-skill/output",
    "key_difference": "技能提供了结构化步骤和验证脚本，而不带技能版本缺乏指导"
  },
  "with_skill_strengths": [
    "清晰的分步指令处理多页文档",
    "包含验证脚本捕获了格式错误",
    "显式的错误回退指导"
  ],
  "without_skill_weaknesses": [
    "缺乏结构化指导导致行为不一致",
    "没有验证脚本，不得不临时凑合而出错",
    "没有错误处理指导，遇到困难就放弃了"
  ],
  "improvement_suggestions": [
    {
      "priority": "high",
      "category": "instructions",
      "suggestion": "将模糊指令替换为明确的步骤：1) 提取文本，2) 识别章节，3) 按模板格式化",
      "expected_impact": "消除导致行为不一致的歧义"
    },
    {
      "priority": "high",
      "category": "tools",
      "suggestion": "添加 validate_output.py 验证脚本",
      "expected_impact": "在最终输出前捕获格式错误"
    },
    {
      "priority": "medium",
      "category": "error_handling",
      "suggestion": "添加回退指导：'如果 OCR 失败，尝试：1) 不同分辨率，2) 图像预处理，3) 手动提取'",
      "expected_impact": "防止在困难文档上过早失败"
    }
  ]
}
```

## 指南

- **具体**：引用技能和 transcript 中的内容
- **可操作**：建议应是具体的变更
- **聚焦技能改进**：目标是改进技能，而非批评执行者
- **按影响排序**：哪些变更最可能改变结果？
- **考虑因果关系**：技能弱点是否真正导致了更差的输出？
- **保持客观**：分析发生了什么，不要做编辑评论

## 建议类别

| 类别 | 描述 |
|------|------|
| `instructions` | 技能说明文字的变更 |
| `tools` | 要添加/修改的脚本、模板或工具 |
| `examples` | 要包含的示例输入/输出 |
| `error_handling` | 处理失败的指导 |
| `structure` | 技能内容的重组 |
| `references` | 要添加的外部文档或资源 |

## 优先级

- **high**: 可能改变对比结果
- **medium**: 会改进质量但不一定改变胜负
- **low**: 锦上添花，边际改进

# 分析基准测试结果

分析 benchmark 数据的目的：**揭示聚合统计可能隐藏的模式和异常**。

## 角色

审查所有 benchmark 运行结果，生成自由格式的笔记，帮助用户理解技能性能。关注聚合指标本身看不到的模式。

## 流程

### 第 1 步：读取 Benchmark 数据

1. 读取包含所有运行结果的 benchmark.json
2. 注意测试的配置（with_skill, without_skill）
3. 理解已计算的 run_summary 聚合数据

### 第 2 步：分析每条断言的模式

对每条跨所有运行的断言：
- **始终通过**（两种配置）→ 可能不能区分技能价值
- **始终失败**（两种配置）→ 可能已损坏或超出能力范围
- **带技能始终通过，不带始终失败**→ 技能显然在此有价值
- **带技能始终失败，不带始终通过**→ 技能可能有反效果
- **高方差**→ 不稳定的断言或非确定性行为

### 第 3 步：分析跨评估的模式

- 某些评估类型是否始终更难/更容易？
- 某些评估是否显示高方差而其他稳定？
- 是否有与预期相矛盾的结果？

### 第 4 步：生成笔记

每一条笔记应该：
- 说明具体的观察
- 基于数据（非推测）
- 帮助用户理解聚合指标未显示的内容

```json
[
  "断言 '输出是 HTML 文件' 在两种配置中均 100% 通过——可能不能区分技能价值",
  "Eval 3 显示高方差（50% ± 40%）——运行 2 有一个不寻常的失败，可能不稳定",
  "不带技能版本在表格提取断言上始终失败（0% 通过率）",
  "带技能版本增加了 13 秒平均执行时间，但通过率提高了 50%"
]
```
