# 双视角评审模式：代码迁移/适配审查

## 场景

当你将一段代码从原始平台迁移/适配到另一个平台时（例如将 Claude Code 技能适配到 Hermes Agent），需要两个独立视角的审查来确保质量。

## 核心原则

不要用一个子代理同时检查两件事。功能一致性和设计合理性需要不同的判断标准。

## 双视角分工

### 子代理 A：功能一致性审查（Functionality Consistency）

**目标**：逐项对比适配版和原版，检查功能是否保留。

**Prompt 模板：**

```
审查 [适配版文件路径] 的功能一致性。

需要与原始 [原版 URL/路径] 对比检查：

1. 核心逻辑是否更改？
   - JSON schema 字段名和结构是否一致
   - 算法/计算公式是否一致
   - 输入/输出接口是否一致
   
2. 功能是否删减？
   - 原版有的功能，适配版是否完整保留
   - 如果有移除，理由是否充分
   
3. 数据格式是否兼容？
   - 字段命名是否一致
   - 是否有新增字段导致下游兼容性问题

对每条检查输出：✅ 一致 / ❌ 不一致（说明差异和影响）
```

### 子代理 B：差异修改合理性审查（Modification Reasonableness）

**目标**：审查代码改动是否合理，是否适合目标平台。

**Prompt 模板：**

```
审查 [适配版文件] 的改动是否合理。

对比 [原版 URL] 的差异，检查：

A. 平台映射是否正确？
   - 原版 CLI 命令是否映射为 Hermes Agent 的正确工具
   - API 调用方式是否适配正确
   
B. 移除的功能是否合理？
   - 被移出的功能在新平台上确实不需要吗？
   - 是否有应保留的遗漏？
   
C. 新增功能是否合理？
   - 新增内容是否与目标平台的工作方式一致？
   - 是否有断裂引用（路径不存在、文件缺失）？
   
D. 工作流可执行性？
   - 指令是否明确可操作
   - 文件路径是否正确
   - 是否有残留的原平台专有命令

对每条检查输出：✅ 合理 / ⚠️ 有问题（说明原因）
```

## 工作流

```
1. 编写适配代码
2. 并行启动两个审查子代理（互不阻塞）
   - subagent-A: 功能一致性
   - subagent-B: 修改合理性
3. 汇总两份报告
4. 修复两个子代理共同指出的问题（优先级最高）
5. 修复单个子代理指出的问题
6. 重新验证（可选）
```

## 何时使用

| 场景 | 适用 | 示例 |
|------|------|------|
| 跨平台代码迁移 | ✅ 强烈推荐 | Claude Code → Hermes Agent |
| 框架升级 | ✅ 推荐 | Vue 2 → Vue 3, PyTorch → TensorFlow |
| 重构 | ⚠️ 可选 | 内部代码重组 |
| 添加新功能 | ❌ 不需要 | 使用 subagent-driven-development 的标准实现+审查模式 |

## 区别于标准 2-阶段审查

`subagent-driven-development` 的标准 2-阶段审查是：
1. **Spec Compliance**：做对了吗？
2. **Code Quality**：做得干净吗？

而双视角适配审查是：
1. **Functionality Consistency**：功能保留了吗？
2. **Modification Reasonableness**：改动合理吗？

前者适用于**实现新功能**，后者适用于**迁移/适配已有代码**。两者可以串联使用：先用双视角审查评估迁移质量，再用标准审查检查迁移后的代码质量。
